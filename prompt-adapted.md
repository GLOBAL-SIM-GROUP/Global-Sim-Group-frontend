# Task: Professionally Configure the TanStack React Frontend

The TanStack React project has just been created.

It is the frontend of **GLOBAL SIM GROUP — SIM**, a multiservice management
platform (résidence, market, pressing, restaurant, salle de fête, facturation,
finances, RH, rapports, administration) backed by a single consolidated
PostgreSQL database.

The **backend and database are already built and deployed in dev**:

* `sim-backend` — API REST **NestJS (TypeScript)**, modular monolith:
  one Nest module per business module under `src/<module>/`.
* `sim-database` — **PostgreSQL 18**, schema-per-module (core, client,
  residence, market, pressing, restaurant, salle_fete, facturation, finances,
  rh, admin, audit), schema evolution owned by **Flyway**, reference + dev
  seeds, pgTAP test suite.
* DB access layer: **Kysely** against a typed schema (`src/db/generated.ts`,
  generated from the real schema by `pnpm db:gen`; `pnpm db:verify` enforces
  freshness). The frontend never talks to the database — API only.
* **Auth**: custom **JWT** bearer auth (access + rotating refresh tokens),
  NOT Keycloak. Login is `POST /api/v1/auth/login` with `{ login, mot_de_passe }`.
* **OpenAPI**: real, live spec generated by `@nestjs/swagger` at
  `https://dev.sim.strife-cyber.org/docs-json` (Swagger UI at `/docs`).
* Object storage: **MinIO** (S3-compatible) for uploads. **Redis** for token
  revocation, rate limiting, jobs. **Traefik** on the VPS.

Deployed dev facts (do not invent anything else):

```text
Frontend origin : https://dev.sim.strife-cyber.org   (backend CORS allows this)
API base        : https://dev.sim.strife-cyber.org/api/v1
Swagger UI      : https://dev.sim.strife-cyber.org/docs
OpenAPI JSON    : https://dev.sim.strife-cyber.org/docs-json
Health          : /api/v1/health/live  /api/v1/health/ready
```

The frontend will eventually cover the 12 business modules of the conception
(M0–M11): Tableau de bord (M1), Résidence (M2), Market (M3), Pressing (M4),
Restaurant (M5), Salle de fête (M6), Facturation (M7), Finances (M8), RH (M9),
Rapports (M10), Administration (M11), on top of M0 fondation transverse

Your task is to turn the generated TanStack project into a **professional,
maintainable, modular frontend foundation** with strong conventions,
documentation, developer experience, internationalization, authentication
boundaries, API boundaries, testing conventions, and scalable project structure.

# 8. Authentication architecture

The backend uses **custom JWT authentication** (access token + rotating refresh
tokens) — there is NO Keycloak, NO external IdP.

The real auth surface (from the live spec):

```text
POST   /api/v1/auth/login      { login, mot_de_passe }     → { accessToken, accessExpiresIn, refreshToken, refreshExpiresIn, utilisateur: { id, login, role } }
POST   /api/v1/auth/refresh    { refresh_token }           → new token pair (rotation)
POST   /api/v1/auth/logout     { refresh_token } + Authorization header
GET    /api/v1/auth/me         (Bearer) → { id, login, role, permissions: string[] }
```

Access JWT claims: `{ sub, login, role, jti }`. Access TTL is short
(`JWT_ACCESS_TTL`, 900s in dev defaults); refresh TTL 7d. Refresh tokens are
**rotated on every refresh** and stored hashed in the DB with lineage — a reused
(replayed) refresh token is treated as family compromise and revokes the whole
token family. The frontend auth layer must therefore:

* silently refresh before/on access-token expiry,
* on refresh failure, treat the session as expired and redirect to login,
* never expose or log tokens.

Establish an authentication boundary under:

```text
src/core/auth/
```

with a small application-level interface:

```text
Feature
   │
   ▼
Auth abstraction
   │
   ▼
JWT implementation (real dev backend)
```

Do not scatter fetch-to-`/auth/*` calls through components.

Do not implement a custom username/password store — passwords never live in the
frontend. The login form calls the real endpoint with `{ login, mot_de_passe }`.

Do not store tokens in `localStorage` if it can be avoided; prefer in-memory
storage or httpOnly cookies if the backend supports them (it does not yet — the
frontend holds the bearer tokens, so document the chosen storage and its XSS
trade-off explicitly).

Document responsibilities:

```text
login
logout
refresh / token lifecycle
session / authenticated state
token handling (storage, injection, expiry)
authentication errors
```

# 9. Authorization architecture

Authentication and authorization are different concerns.

Document this explicitly.

```text
Authentication
→ Who is the user?

Authorization
→ What can the user do?
```

The backend's permission model is a **role → permission matrix stored in the
database**, seeded and managed via `admin` (M11). Permissions are NOT in the
JWT — the backend loads them per request; the frontend gets them from
`GET /auth/me` (`permissions: string[]`, sorted).

Permissions are namespaced by the real modules with three verbs:

```text
<MODULE>.VOIR      (read)
<MODULE>.CREER     (create)
<MODULE>.MODIFIER  (update)
```

The real module prefixes are exactly:

```text
RESIDENCE  MARKET      PRESSING   RESTAURANT  SALLE_FETE  FACTURATION
FINANCES   RH          CLIENT     MARCHANDISE ADMIN       AUDIT
CORE
```

Examples:

```text
RESIDENCE.VOIR
RESIDENCE.CREER
RESIDENCE.MODIFIER
FINANCES.VOIR
RH.MODIFIER
```

There is intentionally **no `DELETE` permission** — delete actions are guarded
by the role matrix in the backend (e.g. `RESIDENCE.MODIFIER`). Do not invent
extra permission verbs.

Create the architectural foundation for:

```text
src/core/permissions/
```

Permissions should be represented as application capabilities derived from the
real `permissions` array of `/me`. The frontend should not guess permission
names from URLs or routes — only the ones the backend actually seeds.

The backend remains responsible for enforcing authorization (`JwtAuthGuard` +
`PermissionsGuard`).

Frontend permission checks are for:

* UI visibility
* navigation
* disabling actions
* improving UX

They are NOT a security boundary.

Document:

> The backend must independently enforce every protected operation.

# 20. Backend error localization

The backend already sends **stable error codes** in a consistent envelope.

Do not make the backend responsible for frontend translations.

The real error envelope on failures is:

```json
{
  "success": false,
  "code": "...",
  "message": "...",
  "details": {},
  "requestId": "...",
  "path": "/api/v1/...",
  "timestamp": "..."
}
```

HTTP status mapping the backend applies: `23505` → 409, `23503` → 422,
`22P02`/`23514` → 400; validation → 400 with `code: "VALIDATION_ERROR"`.
Authentication failures → 401 with `code` set by the auth layer.

The frontend maps codes to localized messages, e.g.:

```json
{ "code": "VALIDATION_ERROR" }

French:
La validation a échoué.

English:
Validation failed.
```

Backend `message` values are French (e.g. `"Identifiants invalides"`) and may
be shown as a fallback, but the primary path is: **frontend maps `code` →
localized message**; the API contract stays stable.

Document this convention.
